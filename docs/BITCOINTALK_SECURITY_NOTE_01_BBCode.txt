[b]Summary[/b]

We deployed a paid [b]useful Proof-of-Work[/b] order on the HackMe coordinator: miners search for inputs where a WASM [mono]check(i64)->i32[/mono] flags a [b]consensus-style violation class[/b] — [mono]OP_PUSHDATA1 (0x4c)[/mono] with claimed push length [b]> 520 bytes[/b] (simplified from Bitcoin Script element-size rules).

A linked fuzz campaign produced verdict [b]clean[/b] on the demo sample (expected for a working guard). Operator reports now open as [b]styled HTML[/b] (not raw JSON) — suitable for screenshots and release notes.

[b]This is not[/b] a claim of a new vulnerability in [b]Bitcoin Core[/b]. It is a [b]reproducible research demo[/b] of how our network runs security-class work (same infra as the live HMC pool and B2B fuzzing).

#![no_std]

use core::panic::PanicInfo;

#[panic_handler]

}

/// Simplified Bitcoin Script push-size rule (educational / research gate).
/// Input packs: opcode in low byte, claimed push length in bits 8..23 (see check()).
/// Returns 1 when the tuple violates the "max push element 520 bytes" style bound.
#[no_mangle]
pub extern "C" fn check(n: i64) -> i32 {
    if n <= 0 {
        return 0;
    }
    let op = (n & 0xff) as u32;
    let claimed_len = ((n >> 8) & 0xffff) as u32;
    if op == 0x4c && claimed_len > 520 {
        1
    } else {
        0
    }
}
