# Подготовка кошелька и сети к листингу на биржах (технический контракт)

Этот документ — **техническая** подготовка: формат адреса, переводов, единиц, API для интеграции. **Не** юридический и **не** гарантия приёма биржей: у каждой площадки свой onboarding (KYC проекта, AML, объём ликвидности, требования к коду и аудиту).

## 1. Идентификаторы сети (что передать в integration-форму)

| Поле | Значение в текущем коде | Комментарий |
|------|-------------------------|-------------|
| **Логический chain id** | `hackme-dev-mainnet` (константа, см. `spec/CHAIN_SPEC.md`, `GET /api/status` → `chain_id`) | Для **прод-листинга** обычно нужен **стабильный** публичный идентификатор и **одна** согласованная цепь; смена `chain_id` = по сути новая сеть для биржи. |
| **Тикер (предлагаемый)** | `HMC` (по префиксу адреса и документации) | Окончательно утверждается с биржей (коллизии тикеров на рынке). |
| **Минимальная единица** | **Kapa** | `1 HMC = 100_000_000` Kapa (`uint64` в API). **Никаких float** в wire-протоколе. |
| **Адрес** | Строка `HMC-` + **16 hex-символов** (нижний регистр), всего **20 символов** с префиксом | Детерминированно из Ed25519 pubkey: `SHA256(pubkey)[:8]` → 16 hex (см. `cmd/minersign`, `tools/scan_ed25519_seeds`). |
| **Подпись перевода** | Ed25519, `transfer_v1` | Поля и порядок ключей для подписи — **`spec/CHAIN_SPEC.md`** раздел «Переводы». |
| **Минимальная комиссия** | `1000` Kapa (`DefaultTransferMinFee` в `internal/chain/transfers.go`) | Меньше — tx отклонится (`invalid_fee`). |
| **Распределение комиссии** | 30% burn / 70% на консенсусный `DevFeeAddress` | См. `docs/API.md` → `POST /api/tx/send`; без runtime-override. |
| **Memo / tag** | Опционально, до **256 байт** UTF-8 | Если биржа выдаёт **deposit memo/tag**, его нужно класть в **`memo`** в теле `transfer_v1` (при поддержке на стороне кошелька/скрипта). |

## 2. HTTP API для интеграции (read + write)

Базовый URL command node (публично): например `https://hackme.tech` (конкретный хост — у оператора).

| Назначение | Метод | Путь |
|------------|--------|------|
| Высота, экономика, `policy_hash` | GET | `/api/status` |
| Баланс и `next_nonce` | GET | `/api/address/{address}` |
| Отправка перевода | POST | `/api/tx/send` |
| Статус tx | GET | `/api/tx/{hash}` |
| Mempool (оператор) | GET | `/api/tx/pool` |
| Блоки (обозреватель) | GET | `/api/chain?limit=…`, `/api/reports/blocks?…` | 

Нормативное описание перевода: **`spec/CHAIN_SPEC.md`**, детали HTTP: **`docs/API.md`**.

## 3. Что биржи часто просят (сопоставьте сами с их PDF)

- **Фиксированные decimals** — у вас **8** (Kapa per HMC).
- **Финальность / подтверждения** — в MVP обычно считается **включение в блок**; явное число «N подтверждений» зафиксируйте с биржей и с `GET /api/tx/{hash}`.
- **Нет reorg / политика вилок** — см. `consensus_policy` в `/api/status` (`no_reorg_v1_fail_closed` и т.д.) — приложите JSON бирже.
- **Genesis, max supply, policy hash** — поля `economics` и `policy_hash` в `/api/status`.
- **Исходный код / воспроизводимая сборка** — репозиторий + `go version`, опционально `reports/pool-freeze-*` из `scripts/ops/pool_release_freeze.sh`.
- **Тестовая сеть** — если биржа требует **отдельный testnet**: поднимите отдельный command node + **новая** БД и **явно другой** `chain_id` (потребует изменения кода/константы и согласования — не смешивать с продом).

## 4. Подготовка кошельков (операционный минимум)

1. **Отдельный «биржевой» кошелёк**  
   - Не использовать тот же seed, что у ноды/казны в открытом окружении.  
   - Сгенерировать ключ: `go run ./cmd/minersign -gen-seed` → сохранить **seed / pubkey / HMC-адрес** в vault (менеджер паролей, HSM — по возможности).

2. **Проверка адреса**  
   - `GET /api/address/<HMC-...>` на каноническом узле должен возвращать ожидаемые `balance_units` / `next_nonce` после тестового пополнения.

3. **Тестовый депозитный цикл**  
   - Малая сумма: `POST /api/tx/send` с корректными `amount_units`, `fee_units >= 1000`, верным `nonce`.  
   - Убедиться, что биржа видит tx по **тому же** `tx_hash`, что возвращает API (hex из ответа).

4. **Memo**  
   - Если биржа дала **destination tag**: включить в `memo` при формировании JSON для подписи (и не обрезать UTF-8 сверх лимита).

5. **Резерв и восстановление**  
   - Офлайн-копия seed; процедура при компрометации — **новый** ключ и новый депозитный адрес у биржи.

## 5. Что отправить команде интеграции биржи (шаблон)

Можно вставить в письмо как приложение:

```
Network name: HackMe (self-hosted command node)
Chain ID (logical): hackme-dev-mainnet   [или ваш прод-id после согласования]
Address format: HMC-<16 lowercase hex>  (example: HMC-0123456789abcdef)
Decimals: 8 (1 HMC = 100_000_000 Kapa)
Signature: Ed25519, tx_type transfer_v1 (see attached CHAIN_SPEC.md § transfers)
Min fee: 1000 Kapa
RPC-style HTTP base: https://<your-command-node>/
Endpoints: GET /api/status, GET /api/address/{addr}, POST /api/tx/send, GET /api/tx/{hash}
Block explorer: https://<your-command-node>/explorer  [если включён]
Policy / economics: GET /api/status → economics + policy_hash
```

Прикрепите файлы из репозитория: **`spec/CHAIN_SPEC.md`**, **`docs/API.md`** (раздел transfers).

## 6. Чего в коде **пока нет** (не обещать бирже без доработки)

- Официальный **SLIP-0044** coin type для HD-кошельков.  
- Стандартизированный **gRPC** вместо JSON HTTP.  
- **Аппаратный кошелёк** (Ledger и т.д.) — отдельный проект.  
- Автоматический **bridge** в другие сети.

Итог: **подготовить к листингу** с текущим стеком можно как **HTTP-интеграцию + фиксированный wire-формат + отдельные ключи и тестовые переводы**; «всё по правилам бирж» в юридическом смысле проходит **только** через их чеклисты и юристов проекта.
