Miner quick path

Recommended flow for public pool participation (coordinator + worker)

  1. Install the node from Downloads and verify checksums.
  2. Set HACKME_POOL_COORDINATOR_URL to your pool coordinator HTTP base (see Docs). Optionally set HACKME_CANONICAL_CHAIN_URL / HACKME_P2P_PEERS so local height and mempool match the network.
  3. Open the dashboard → install genesis once → Start worker on the Mining tab. Payout accrues on the coordinator; on-chain balance follows the public chain after settlement.

Block subsidy on the canonical producer credits that node's primary wallet; fleet rewards flow through coordinator accrual, not automatic per-GPU splits of every block. See Economics: chain, pool & orders.

How to Start Mining

From zero to first accepted work in a few minutes.

  1. Download the node bundle from Downloads and run your platform installer.
  2. Open local dashboard, set admin token, and verify node health + wallet address.
  3. Connect worker mode to the pool coordinator and start mining (POST /api/worker/start).

Proof of Analysis (Utility Algorithm)

HackMe is not a random-number lottery. Paid audit jobs are split into deterministic fuzzing/analysis segments. Workers are rewarded for processing unique input ranges that exercise real code paths and surface real findings, so each watt maps to measurable security work.

  • Order payload is partitioned into work chunks with traceable assignment and completion.
  • Each accepted result is tied to unique input space, campaign context, and runtime metadata.
  • Reports aggregate coverage, crashes, and vulnerability evidence for auditors and clients.

Tokenomics and Halving Cycles

Parameter Current Policy Why It Matters
Initial Base Reward 0.010000 HMC per empty-mining block Predictable miner baseline before order bonus layer.
Halving Schedule Every 2,102,400 blocks Programmable long-term inflation reduction toward tail floor.
Tail Floor 0.002000 HMC Maintains liveness and security budget after multiple halvings.
Transfer network fee split 70% dev/service · 30% burn Applies to fee_units on signed transfers — not to opening orders.
Order platform fee 5% of prepaid Credited to the consensus dev/service address when the order is created.
Order-open burn tally 10% of prepaid OrderBurnRate: counted toward aggregate burned supply at creation (see chain economics).

Policy fields are exposed via public APIs and release gates for auditability.

Orders vs transfers (burn accounting)

Opening an order debits your wallet once for escrow plus platform fee. Transfer transactions burn part of their fee_units separately:

prepaid = reward_hmc × target_solves
order_fee = prepaid × 0.05 → dev/service
burn_recorded = prepaid × 0.10 (supply tally)
wallet_debit = prepaid + order_fee

Example: 1000 HMC prepaid workload → you pay 1050 HMC up front (1000 escrow + 50 platform fee). Supply accounting adds 100 HMC burned from the prepaid bucket (OrderBurnRate). Transfer fees still split 70% / 30% dev vs burn.
