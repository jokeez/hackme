Economics model

Chain rewards, coordinator payouts, and orders

HackMe is intentionally not a clone of classic pooled Proof-of-Work (where every hash‑rate share maps directly to a fraction of each chain block). Three layers work together: on-chain PoH, coordinator accounting, and paid audit orders.

Where value comes from

Source What it is Who receives it (typical) Where you see it
Base PoH block Scheduled emission when the solved block is not tied to an open paid order task (halving + tail floor). The node that successfully appended the block credits its primary wallet (chain accounting). Explorer block metadata; node wallet balance for that producer.
Order-linked PoH block Block reward must match the open task's escrowed reward; emission is constrained by order economics. Same primary-wallet credit path on the producing node, funded from task escrow. Task / order APIs; block tied to orderTaskID context.
Coordinator pool Off-chain accounting for leased ranges, accepted attempts, bonuses — operator policy. Workers per pool rules; settled to on-chain balances via automation you configure. Dashboard work stats, total_payout_hmc, settlement scripts.

Figures such as base reward, halving interval, tail floor, and fee splits are also summarized on the home page and in docs/ECONOMICS_DASHBOARD.md alongside /api/metrics fields.

Critical nuance: block header vs wallet credit

When a PoH reward is minted, the implementation credits the primary wallet row on that node so GET /api/wallet stays consistent with accounts. The block still records a miner address (signer at solve time) for transparency.

  • If those diverge after backup or wallet rebind, crediting the header address alone could strand balances — so credits follow the primary wallet.
  • This is not the same as "every GPU in the pool automatically earns a pro‑rata slice of each new block" unless your operator policy explicitly implements that via coordinator settlement.

Why we separate chain and pool

  • Consensus cadence: PoH keeps difficulty and tip progression honest.
  • Useful work: Coordinator metrics tie fleets to measurable throughput and anti‑abuse (replay, stale work, hybrid signer).
  • Product economics: Audit orders bring escrow, fees, burns, and WASM‑gated tasks — the main demand layer for useful compute.

Expectations for miners: treat coordinator accrual and settlement as your primary "pool paycheck" story unless you operate the block-producing node yourself.

Public pool: how your rig earns (fair mode)

On the official pool, coordinator payout uses accepted attempts (capped per lease batch), tied to canonical economics via reward_per_m, plus a found bonus when you submit a valid hit.

accrual ≈ (attempts / 1,000,000) × reward_per_m + found_bonus (on valid found)
reward_per_m ≈ base_reward × 1,000,000 / target_mod (auto from chain metrics)
  • Set WORKER_PAYOUT_MAP so your worker id maps to your HMC-… address before expecting settlement.
  • Unpaid worker accrual on the dashboard is the pool paycheck story; on-chain balance updates after settlement runs.
  • Hybrid signing + per-worker lease caps keep the pool fair when many miners join.

Full miner guide: MINER_POOL_ECONOMICS.md

Network-wide intuition vs your rig

Empty‑mining emission is capped by protocol schedule (roughly ~120 blocks/hour at a 30s target). Adding more miners does not inflate total base emission; it changes how competitive finding the next valid block is.

Your coordinator-facing income still follows accepted work and payout policy — consult your operator dashboard and settlement configuration.
